## What to build

Ticket 017 walks SELECT-list subqueries and derived tables, but two EXPLAIN JSON node types are still skipped, so their table accesses are never analyzed:

- `attached_subqueries` — subqueries in a WHERE condition (e.g. a dependent `EXISTS` generated by `whereHas`). Staging 0185db31: the only reason reported is `merchants.deleted_at` being weak, while the dependent `EXISTS` on `adjustments` (`ref` on `merchant_id`, `type` checked on rows) is never looked at.
- `optimized_away_subqueries` — subqueries MySQL evaluates once and folds into a constant. Staging 8c9a4128.
- `having_subqueries` — subqueries in a HAVING condition (added in review: MySQL 8.0 and 8.4 report a HAVING subquery here, not under `attached_subqueries`).

Walk both node types wherever they appear (inside `query_block`, `nested_loop` entries, `table` nodes, `ordering_operation` / `grouping_operation`), and attribute each inner table access to the inner query's columns using the same parser-based extraction already used for `EXISTS` (ticket 004) and SELECT-list subqueries (ticket 017). A Fingerprint whose outer table has only weak predicates but whose subquery yields a Suggestion is no longer listed as skipped for the outer table alone — it gets the Suggestion, and the outer-table reason only appears if nothing else was suggested.

Impact attribution stays as today: the Fingerprint's measured `count × avg_ms` (the dependent subquery's cost is already inside that latency). No outer-row multiplier.

## Review decisions

- (agent, pending user confirmation) The driver's plan walk already recursed into every nested node, so both node types were reached; the gap left after ticket 022 was the reporting. Only the "only low-selectivity predicates" reason is dropped for a Fingerprint some final Suggestion serves (on any of its tables, not only the outer one). Other reasons on the same Fingerprint (no indexable predicate columns, several table references with that name, another database, only columns written by frequent UPDATEs) are still listed, because they say the analysis was incomplete or are ticket 021's own decision. Ticket 025 may change this when it splits skipped from unparsed.
- (agent, pending user confirmation) The walk is bounded by the plan's JSON decoding depth, `MySqlDriver::PLAN_DEPTH` = 4,096 levels (it was `json_decode`'s default of 512). MySQL 8.0 and 8.4 reject nesting past about 64 levels ("Too high level of nesting for select"), but one level can take 10 JSON levels or more: a plan recorded with 64 levels of a derived table holding a UNION under a GROUP BY was 634 levels deep, which 512 failed to decode. 4,096 leaves 64 JSON levels per query block. A deeper plan fails as `EXPLAIN failed (JsonException)` (no SQLSTATE: only a PDOException's code is reported as one). A decoded JSON tree has no cycles, so the walk cannot loop.
- (agent, pending user confirmation) HAVING subqueries (`having_subqueries`) are analyzed like WHERE ones: the Column extractor reads the subqueries of a HAVING condition as their own scopes, correlated columns included, but not HAVING's own predicates, which filter groups (often on an aggregate or its alias), not rows an index could seek.
