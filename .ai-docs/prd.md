# PRD: db-hound v1

## Problem Statement

Engineers on Laravel applications backed by MySQL find missing indexes reactively: after an endpoint or job is already slow in production, after a customer complains, or after an incident. Local and CI databases are too small to reveal the problem — MySQL happily full-scans a 200-row table — so the queries that matter are only visible under real production data and real access patterns. Even when a slow query is spotted, working out the *right* index (column order, whether an existing index can be extended, whether another query needs an overlapping index on the same table) is manual, error-prone work, and naive fixes pile up near-duplicate indexes on hot multi-tenant tables.

## Solution

db-hound is a Laravel package that, when enabled in production, samples the application's queries with negligible overhead, aggregates them by **Fingerprint** (normalized SQL shape), and stores them. An engineer runs `php artisan db-hound:analyze` on a production host; it runs `EXPLAIN` on the most impactful Fingerprints against a (preferably replica) connection, extracts predicate columns with a real SQL parser, compares against existing indexes, and writes a self-contained Markdown **Report** of ranked index **Suggestions**. The engineer copies the Report to their machine (SCP), where a local coding agent reads it and writes the Laravel migrations in a pair session with the engineer. The package never runs DDL itself.

For deeper investigation, `php artisan db-hound:dump` writes a sensitive JSONL **Dump** with decrypted Samples and raw `EXPLAIN` output for the agent to analyze further.

## Glossary

- **Fingerprint** — normalized SQL shape of a query (literals stripped, `IN` lists collapsed, whitespace/comments normalized) plus its hash. Aggregation key.
- **Sample** — one example of a Fingerprint's query with real bindings, stored encrypted with a TTL. Used only to run `EXPLAIN`.
- **Store** — where captured aggregates live before and after flushing (Redis driver, file driver).
- **Suggestion** — a proposed index (new or extension of an existing one) on a table, with reasons and impact.
- **Report** — Markdown file of ranked Suggestions plus all context needed to write migrations without production access. Contains no bindings.
- **Dump** — JSONL file with everything, including decrypted Samples and raw `EXPLAIN`. Always sensitive.

## User Stories

### Enabling & configuring capture
1. As an engineer, I want db-hound to be disabled by default, so that installing the package never changes production behavior until I opt in.
2. As an engineer, I want to enable capture with an environment flag, so that I can turn it on per environment without a deploy of code changes.
3. As an engineer, I want to set a sample rate, so that I can bound the overhead on production traffic.
4. As an engineer, I want sampling to be decided once per request or job, so that a sampled unit of work captures all its queries and frequency counts stay proportional.
5. As an engineer, I want a minimum query duration threshold, so that trivially fast queries are not captured.
6. As an engineer, I want connection allow/deny lists, so that I can limit capture to the MySQL connections I care about.
7. As an engineer, I want table allow/deny lists, so that I can exclude tables irrelevant to indexing.
8. As an engineer, I want db-hound's own queries always excluded, so that the package never analyzes itself.
9. As an engineer, I want capture to work in HTTP (FPM), Octane, queue workers and Artisan commands alike, so that slow background jobs are covered, not just web requests.

### Capture performance & safety
10. As an SRE, I want queries aggregated in memory and sent to Redis in pipelined batches of 50, so that a sampled request with hundreds of queries only pays a few milliseconds.
11. As an SRE, I want any remaining batch pushed at process shutdown, so that short-lived processes don't lose their tail of queries.
12. As an SRE, I want capture to fail open with a hard Redis timeout, so that a Redis outage never breaks or blocks a request.
13. As an SRE, I want capture failures logged at most once per minute, so that an outage doesn't flood the logs.
14. As an engineer, I want queries that differ only in literal values or `IN` list length to share one Fingerprint, so that impact is not fragmented across near-identical entries.

### Samples & sensitive data
15. As a security-conscious engineer, I want Samples encrypted at rest with the app key, so that production values in Redis and the database are protected.
16. As a security-conscious engineer, I want only one Sample per Fingerprint with a 7-day TTL, so that sensitive values don't accumulate.
17. As a security-conscious engineer, I want a switch to never store real bindings, so that teams with strict policies can still use the package with placeholder-based `EXPLAIN`.
18. As a security-conscious engineer, I want the Report to never contain bindings or raw `EXPLAIN` literals, so that it is safe to copy to a laptop.

### Flushing & retention
19. As an SRE, I want a scheduled `db-hound:flush` that moves Redis aggregates into a database table when a size threshold is exceeded, so that Redis memory stays bounded.
20. As an SRE, I want the flush to also trigger when the oldest buffered data exceeds an age threshold, so that quiet apps don't lose data to Redis eviction.
21. As an engineer, I want the flush to snapshot data atomically, so that increments arriving during a flush are never lost.
22. As an engineer, I want a scheduled daily `db-hound:prune` that deletes Fingerprints not seen for 30 days (configurable), so that removed code paths disappear from Reports.
23. As an engineer without Redis, I want a file Store driver, so that I can use db-hound on a single-server app.

## Implementation Decisions

- **Engine:** MySQL 8+ only. All engine-specific behavior (`EXPLAIN` execution and interpretation, index/column/row-count inspection) lives behind a `Driver` interface so Postgres can be added later. MariaDB is best-effort.
- **Modules:**
  - **Fingerprinter** — fast tokenizer on the hot path: strips literals and comments, collapses `IN (?, ?, …)` to a single marker, normalizes whitespace, hashes. No AST.
  - **Recorder** — listens to Laravel's query-executed event; decides sampling once per request/job; applies thresholds and allow/deny lists; excludes db-hound's own tables; aggregates per Fingerprint in memory (count, total ms, max ms, first/last seen, connection, one Sample).
  - **Store** (interface) — `push(batch)`, atomic `snapshot()`, size/age introspection. Drivers: Redis (primary), file (fallback, JSONL appended per process, rotated on flush). Store writes from the hot path must fail open.
  - **Repository for `db_hound_queries`** — persisted aggregates: fingerprint hash, normalized SQL, encrypted Sample, count, total/max ms, first/last seen, connection. Upsert merges counts. This is the only package table in v1 (no suggestions table).
  - **Driver (MySQL)** — `explain(sql, bindings)` returning a normalized plan; schema inspection (existing indexes from `information_schema.STATISTICS`, row counts from `information_schema.TABLES`, column types, per-column cardinality from the `STATISTICS.CARDINALITY` of the B-tree indexes a column leads; the Analyzer falls back to column type heuristics — 2 for a boolean, the members of an enum — for a column that leads none). Schema metadata is looked up once per table per analyze or dump run.
  - **Column extractor** — uses `phpmyadmin/sql-parser` to extract per-table predicate columns, classifying equality vs range vs sort/group; resolves aliases, joins, subqueries/`EXISTS`, correlated subqueries in the SELECT list (`withCount`, `withSum`) and derived tables (subqueries in FROM, e.g. `laravel_table`, `latestOfMany`), whose inner tables EXPLAIN reports under the derived table's materialization, as well as subqueries in GROUP BY and ORDER BY, each part of a UNION inside a subquery, and the tables of a parenthesized join (`a left join (b inner join c on …) on …`, its first table taking the outer join's condition, a `USING` inside it read against its own tables alone); the same table read in two of those places (two parts of a UNION, a whereHas and an ORDER BY subquery) is told apart by where the plan reads it; a derived table's own full scan is expected and never listed. The table accesses of subqueries EXPLAIN reports under `attached_subqueries` (a WHERE subquery MySQL does not turn into a semijoin, such as a whereHas `EXISTS` inside an `OR`, often dependent), `having_subqueries` (a subquery in HAVING; HAVING filters groups, so only its subqueries' own predicates are read) and `optimized_away_subqueries` (one it evaluates once into a constant, such as `select exists(…)`) are analyzed like any other, at any depth and wherever the plan nests them; the plan's JSON decoding depth (4,096 levels, far past what MySQL's nesting limit of about 64 query blocks reaches) bounds the walk. Their impact is the Fingerprint's `count × avg_ms`, which already holds a dependent subquery's cost (no outer-row multiplier). Unparseable queries are surfaced, not dropped, each Fingerprint once per reason.
  - **Analyzer** — qualifies Fingerprints, runs `EXPLAIN` via the Driver, detects symptoms, builds composite candidates (ERS order), consolidates across Fingerprints, dedupes against existing indexes, prefers extending an existing index, ranks by impact. Pure given its inputs (records + Driver).
  - **Report renderer** — Suggestions + context → Markdown with a fixed structure.
  - **Dump writer** — JSONL, one Fingerprint per line.
- **Capture flow:** aggregate in memory per process → when the batch reaches 50 queries, one pipelined Redis write → remainder pushed at shutdown (shutdown function / destructor). No reliance on request/job lifecycle events. Redis connection has a ~50 ms timeout; errors drop the batch and log at most once per minute.
- **Samples:** encrypted with Laravel's encrypter (app key), one per Fingerprint (first-write-wins until TTL), 7-day TTL. `store_bindings=false` stores no values; `EXPLAIN` then uses type-appropriate placeholders. Decrypted only in memory for `EXPLAIN`, and in the Dump.
- **Flush:** scheduled every minute; acts when buffered Fingerprint count or size exceeds a threshold (e.g. 5,000 / 10 MB) OR the oldest buffered data exceeds an age threshold (e.g. 6h). Redis data is snapshotted with `RENAME` before reading so concurrent increments are never lost.
- **Prune:** scheduled daily; deletes rows with `last_seen` older than `prune_after_days` (default 30). Analysis has no separate time window — retention defines it.
- **Analysis connection:** config maps each captured connection to an analysis connection (e.g. `mysql → mysql_replica`); defaults to the same connection. Guards: plain `EXPLAIN FORMAT=JSON` only, `SELECT` only (writes rewritten), read-only transaction, session `max_execution_time`.
- **Qualification defaults (all configurable):** count ≥ 10 AND (avg ≥ 50 ms OR max ≥ 500 ms); ignore tables `migrations`, `jobs`, `failed_jobs`, `sessions`, `cache`, `telescope_*`, db-hound's own; ignore `information_schema`/`SHOW`/`SET` queries; top 200 by impact; skip tables under 1,000 rows.
- **Symptoms flagged:** `access_type = ALL`; **full index scan**: `access_type = index` (every entry of the index read) with a condition checked on each (`attached_condition` or `index_condition`, read only for whether there is one) and a predicate of the query on that table (an equality, a join equality once the table it joins is read, an `IN` list, a range, `IS NULL`, `IS NOT NULL`; not a negation) on a column the index does not hold, its InnoDB primary key suffix included (`audit_logs` read through `(created_at)` for `ORDER BY created_at LIMIT` checking `status = ?` gets `(status, created_at)`; a covering scan with no condition, or one whose condition columns the index holds, is no symptom); `key` NULL with high examined rows; "Using filesort"; "Using temporary"; **partial index use**: a `ref` / `range` access seeks on only some parts of its index (`used_key_parts`) while the plan checks other predicates of the same table row by row (an `attached_condition` or `index_condition`, read only for whether there is one, since its text holds the literal values), and the index the table needs (built by the normal pipeline) has a predicate column (equality, `IN`, `IS NULL`, range, including a range on a later key part a gap blocks) the access does not seek on. No rows-examined gate: the table-rows qualification threshold keeps small tables out. The weak filters it checks row by row stay in that index (after its selective seek columns), and dedupe and consolidation keep them, since they are why the index is suggested. When several ranges qualify, the index seeks on the one on a later key part of the access's index (the one a key gap blocks), whatever the query order. It is not flagged when that index would lack a column the access seeks on, would seek on another range than the one the access seeks on, would break an `ORDER BY` the access's index serves without a filesort (a `GROUP BY` reads every row it seeks anyway, so the note says the new index adds a temporary table and names keeping the current index as the alternative), or adds only weak filters without extending, after the columns it seeks on, an index the access seeks on in full (else it would be a second index on the same leading columns that barely narrows the read), except an `IS NULL` past a key gap: when the access seeks on a key-like column (by its type: `char(36)`, `binary(16)` or an integer `*_id`) and the query leaves the next part of its index unconstrained, that index cannot seek on the `IS NULL` even extended, so the index the table needs is suggested (`notifications` read through `(notifiable_id, notifiable_type, type, created_at)` on `notifiable_id` alone, checking `read_at IS NULL` on the rows, gets `(notifiable_id, read_at)`; decision, user, 2026-11-08). **Fan-out gate (decision, user, 2026-11-08):** nor is it flagged when each seek finds few rows: an equality or an `IN` list (not a null-safe `<=>`, which finds every NULL statistics do not count) pins every column the access seeks on, and MySQL's statistics, trusted on a table of at least `analysis.min_rows_for_cardinality` rows, give fewer than twice a handful (`Selectivity::HANDFUL_OF_ROWS` × 2 = 20) rows per key (table rows / the `CARDINALITY` of the used prefix, taken from its column with the most distinct values, since statistics exist only for a column that leads an index and the prefix has at least as many: an upper bound of the average, not of any one key's rows), and the plan's own estimate of the rows the access examines (`rows_examined_per_scan`, for the values it was explained with) agrees, since an average hides a skewed key (a few large merchants among many small ones); the larger of the two is the ~N reported, rounded down. Checking the rest on so few rows is cheap, and the extension would cost every write (`(merchant_id, is_active)` for 3 branches per merchant), so the query goes to the "skipped" section naming the index and its ~N rows per key, listed only when no Suggestion serves it. When the plan sorts the rows of that access with a filesort and no temporary table (it drives the join, so the sort runs on the rows it finds before any join), sorting so few rows is as cheap: the filesort is dropped too, and with no other symptom the query is skipped the same way (`filesort, partial index use …, and sorting them, is cheap`), so `(merchant_id, is_active, created_at)` is not suggested for 3 branches per merchant ordered by `created_at`; a temporary table may hold more rows than the access finds, so its sort keeps the usual demand, without the partial index use. Without trusted statistics on any column the access seeks on, it is flagged as before. **Decision (user, 2026-11-08):** it is never flagged when each seek finds at most one row: the columns the access seeks on hold every column of a unique index or the primary key, each pinned by an equality or an `IN` list (a join equality only once the table it joins is read; a null-safe `<=>` only on a primary key column, since it may match every NULL of a unique one) (an Eloquent eager load `id in (?) and deleted_at is null`, a `range` on `PRIMARY`), so checking the other predicates on the rows is free (`const` and `eq_ref` accesses are never flagged at all). A predicate on a soft-delete column (the configurable `analysis.soft_delete_columns`, default `['deleted_at']`) matches nearly every row, so it never makes a partial index use on its own: the plan checking only it on the rows is no symptom, and it is not among the columns the index must keep for being checked on the rows; it may still trail an index the access's other predicates call for, as any weak filter does. Other `IS NULL` predicates (such as `notifications.read_at IS NULL`) still make one. A plan with no other symptom whose SQL the parser cannot read, or whose tables cannot be inspected, is passed over silently: it is listed neither as skipped nor as unparsed (a full index scan likewise). **Likely misplan (ticket 030):** before a Suggestion is made, the existing indexes are checked against the query's predicates on the table: when one other than the index the access reads, visible, B-tree, listed in the access's `possible_keys`, leads with a column of the candidate index the access does not seek on, and that column seeks as selectively as the candidate's leading column (an equality or `IN` list on a column that finds only a handful of rows, by statistics, else a key-like type, and with no fewer distinct values than the candidate's leading column when both have statistics; by statistics only when it is the candidate's own leading column, since whether that column's rows are a handful is the fan-out question the gate answers only with statistics; or, on a table under `analysis.min_rows_for_cardinality` rows and only when the plan was explained with the Fingerprint's Sample, a `LIKE`, which MySQL lists the index for only with a constant prefix (a placeholder binding has no wildcard, so without a Sample a `LIKE` never fits), when the candidate's leading column does not find a handful), no Suggestion is made and the query goes to the "skipped" section: "the existing index `X` fits; the plan likely picked another because the table is small or its statistics are stale" (naming the column type when a key-like type, not statistics, decided the handful), listed only when no Suggestion serves it; of several such indexes, the one whose leading columns the query pins most. Never for an access of a subquery the plan marks dependent (it reads those rows once per outer row). An existing index that serves the candidate outright (dedupe) also gets that entry (without the type note) when the access's `possible_keys` lists it and the access reads another; otherwise (the access reads it, or the plan lists no `possible_keys` with it) it drops the candidate silently. **Per-table degrade (ticket 030):** a table whose lookup fails after `EXPLAIN` (missing, lookup error) is reported alone in the "unparsed" section ("<symptoms> on `t`, but inspecting it failed (…)") when the plan shows a symptom on it, and the Fingerprint's other tables are analyzed as usual (it is accounted for as explained, or as other when no table with a symptom could be inspected); the parser takes such a table to have any column, so an unqualified column it may have is never placed in another table, nor placed in it when a table of an outer query may have it (a correlated column): it is unresolved instead. A lookup failing before `EXPLAIN` (the placeholder types of a Fingerprint without a Sample) still fails the whole Fingerprint.
- **Column ordering:** selective equality → weak filters → range → sort. Equality columns can be reordered freely inside an index, so selective equality columns (multi-value `IN` lists included, when no sort follows) are ordered by descending cardinality (index statistics, else the type estimate); ties, and columns without an estimate (placed after those with one), go alphabetically, so the same column set always produces the same candidate. That order is only a preference: when another Fingerprint's index, or an existing index, needs the same equality columns in another order, the Suggestion takes that order instead, so consolidation, dedupe and extend-existing still apply (the selective block always stays ahead of the weak one). **Weak filters** are predicates that match most rows and so must never lead an index: `IS NULL` (e.g. a soft-delete `deleted_at IS NULL`), `IS NOT NULL`, and equality or `IN` on low-cardinality columns — booleans (`tinyint(1)`), enums, and any column so few distinct values that one value matches more than the configurable `analysis.low_selectivity_share` of the rows (1 / `CARDINALITY` above it; default 0.1, i.e. fewer than 10 distinct values). The share, not distinct values per row, because an equality narrows a table of any size to the same share of it: a tenant column stays selective on a huge table. Index statistics are trusted only on a table of at least the configurable `analysis.min_rows_for_cardinality` rows (default 1,000, the table-rows qualification default): on fewer, `CARDINALITY` says nothing (a tenant column of a 6-row table has 1 or 2), so it is ignored and selectivity comes from the column type alone (booleans, `tinyint(1)`, enums, `IS NULL` and `IS NOT NULL` stay weak, every other equality column is selective), and the equality columns fall back to the alphabetical tie-break, which consolidation, dedupe and extend-existing still reorder as they need. Weak filters go right after the selective seek columns (same ordering rule); with no selective seek column they are left out, so `deleted_at IS NULL ORDER BY created_at` suggests `(created_at)`. An `IS NOT NULL` is a range, and a weak `IN` list breaks a sort, so each is kept only at the end of an index with no range or sort after it. A candidate made only of weak filters is not suggested: the query goes to the "skipped" section with the reason "only low-selectivity predicates", unless a Suggestion serves it (on another of its tables, such as that of a whereHas `EXISTS` around which the outer table is filtered only on `deleted_at IS NULL`). When a range column means the index can't satisfy ORDER BY, the Suggestion includes an alternative note ("filesort remains; consider equality → sort → range if the range matches most rows"), leaving the call to the engineer and agent, since db-hound can't reliably know range selectivity.
- **Write-hot columns:** an index is maintained on every write to its columns, so a Suggestion never indexes a column frequent UPDATEs write. The columns written by the captured UPDATE Fingerprints on a connection and table are their `SET` targets, read with the SQL parser (`SET a = a + 1` writes `a`; a multi-table UPDATE's column goes to the table its qualifier or alias names, or, unqualified, to the only one of its tables that has it; an UPDATE the parser can't read, one longer than 16 KB (parsing a bulk UPDATE takes long), a database-qualified column and an ambiguous one are ignored). Only UPDATEs naming a table some Fingerprint demands an index on are parsed, and only when one does. A column of a consolidated Suggestion is **write-hot** when those UPDATEs ran, summed, at least as often as the Fingerprints it serves that need the column (their own candidate has it), and at least `analysis.hot_update_min_count` times (default 100; a short capture's "2 writes vs 1 read" says nothing, decision ticket 031): the whole index is weighed, not each Fingerprint's part, so reads that share the index add up. "Frequent" is relative: every captured UPDATE counts, explained or not (the explain cap and the qualification thresholds don't apply), except one the Suggestion serves itself, whose write is the price of its own lookup. The index of each Fingerprint that needs a write-hot column is built again as if the query did not filter or sort on it (without the range, the sort may be served; without a sort column, the sort goes, and a weak `IN` list it had pushed out is back), and the Suggestions are consolidated again, until no write-hot column is left. When nothing is left of a Fingerprint's index, only weak filters are left, or an existing index already serves the rest (dedupe), it makes no Suggestion and goes to the "skipped" section with the reason "only columns written by frequent UPDATEs" (and the low-selectivity predicates or the existing index). A final Suggestion that does not have a column left out for one of its Fingerprints carries one note per such column, naming the UPDATE Fingerprints writing it (their first 200 characters), with their counts, and how often its served Fingerprints that needed it ran; then extend-existing and ranking proceed as usual.
- **Primary key suffix:** InnoDB appends the primary key columns a secondary index lacks (in primary key order) to it, and the optimizer seeks and sorts on them. A Suggestion leaves out the longest tail of its columns that is exactly that appended suffix (composite primary keys included; a primary key column followed by another column stays), and dedupe compares a candidate against each existing index with its primary key suffix appended. Consolidation still compares the columns the queries need, so `ORDER BY created_at, id` is never folded into an index that puts another column between `created_at` and the key. Only InnoDB tables (the Driver reports each table's engine): MyISAM and MEMORY store a row pointer in secondary indexes, so on them the key is neither left out nor appended. Extending an index drops the order its appended key gave it (`(a, b)` serves `(a, b, id)`, `(a, b, c)` does not), which the queries using it may rely on without a symptom db-hound sees, so the Report's Kind line warns about it whenever the new index does not keep that order.
- **Suggestion scope:** composite indexes (equality → range → sort), consolidation across Fingerprints (left-prefix containment, equality columns in any order, weak filters in any order or left out, since a query filters the rows an index returns on a weak filter the index lacks; a Suggestion several others serve goes to the one with the most impact), a fold on a selective leading column (on the same table, a Suggestion whose queries filter with an equality on the leading column of another's index, when that column finds only a handful of rows (at most 10 per distinct value by index statistics on a table large enough to trust them, else a key-like type: `char(36)`, `binary(16)` or an integer `*_id`; statistics exist only for a column that leads an index, so a tenant key no index leads is taken as key-like by its type), is folded into it: the queries check their other predicates on the rows that column finds, and a second index leading with it would cost every write for no read gain; the surviving Suggestion keeps its columns, its leading column, the columns the folded queries seek on and those that keep their sort fixed in that order (so extend-existing never moves them), serves both sets of Fingerprints and carries a note naming the folded queries' other predicates and, when the column's type and not its statistics decided that it finds only a handful of rows, saying so ("assumed from the column type", naming the type), so an engineer or agent can override the fold (decision, user, 2026-11-08); Suggestions are taken most impact first, ties by their column list, each folding into the first kept one whose index serves it, or, when both lead with the same column and only its own index serves both, that one into it; never when the shared column's statistics show more than a handful of rows, nor when the folded queries would lose an `ORDER BY` or `GROUP BY` order their own index gives them; **decision (user, 2026-11-08):** never either when the folded one serves a subquery the plan marks dependent (a `SELECT`-list subquery such as a `withCount`, an attached or `EXISTS` subquery MySQL runs once per outer row, which multiplies "a handful of rows" by the outer rows; not an `IN` subquery MySQL materializes once, though EXPLAIN marks it dependent), nor into one that serves only such subqueries (a kept index an outer query needs may also serve a dependent subquery by left-prefix containment, and others still fold into it), nor when the kept index has the range the folded queries' own index seeks on after a column they do not pin with an equality, `IS NULL` or `IN` list (a key gap: `(merchant_id, deleted_at, transaction_date)` would not seek on the `transaction_date` range of a query without `deleted_at`, reading every row of the merchant): the two stay separate Suggestions, neither folded into the other, consolidation and dedupe unchanged), dedupe against existing indexes by the left-prefix containment rule (not the selective-lead fold), extend-existing-index proposals (when several existing indexes are prefixes of a Suggestion, it extends the one `EXPLAIN` reports as `key` (or among the indexes of an `index_merge`) for its most impactful served Fingerprint, whose plan the Report's EXPLAIN summary shows, reordering its equality columns to start with it, since that is the index whose replacement changes the plan; else the longest prefix, then the most selective first column; the Report's Kind line names the chosen index and why).
- **Ranking:** impact = `count × avg_ms`.
- **Report:** written to the local storage disk under a db-hound directory as `report-{timestamp}.md` and `latest.md`. Header: run time, connection(s), capture coverage (first/last seen range), thresholds, and a Fingerprint accounting that sums to the Fingerprints analyzed (explained, skipped by row threshold, EXPLAIN failed, no Sample available, skipped by the explain cap, below count/latency thresholds, skipped by ignore lists, not a SELECT/UPDATE/DELETE, other); above it, a warning naming each qualification threshold (Fingerprint count, average and max latency, Table rows; not the explain cap, which bounds the run's cost and not which Fingerprints qualify) looser than its package default next to that default, since Suggestions on small tables are then likely noise. Then a summary table of every Suggestion (rank, table, proposed columns, new vs extend, reasons, impact, Fingerprints served), then one section per table, ordered by the summed impact of its Suggestions, giving the table's context once (row count, existing indexes, column types) followed by its Suggestions by impact. Per Suggestion (with its table's context): table, row count, proposed columns in order, proposed index name, new vs extend, reason(s), `EXPLAIN` summary (`type`, `key`, `rows`, extras), existing indexes on the table, column types of involved columns, count/avg/max/impact, 1–3 example Fingerprints. Then a "Skipped queries" section (flagged Fingerprints db-hound read and decided no index helps: only low-selectivity predicates, only columns written by frequent UPDATEs, only negations (`!=`, `<>`, `NOT column = value`, `NOT IN (…)` of values), a partial index use whose seeks find too few rows (the fan-out gate: "finds ~N rows per key"), an existing index that already fits (a likely misplan: "the existing index `X` fits; the plan likely picked another because the table is small or its statistics are stale"), or no predicate on the table at all, which, like only low-selectivity predicates, the fan-out gate and an existing index that fits, is listed only when no Suggestion on another of the query's tables serves it) and an "Unparsed queries" section (the parser, `EXPLAIN` or a table lookup failed (after `EXPLAIN`, for that table alone), the Fingerprint cannot be explained without a Sample, or the query has a shape db-hound cannot attribute: a plan table matching no table reference or several, another database's table, a column it cannot place, whatever else the table is filtered on, or predicates it does not read as an index's though an index may serve them, such as an `OR`, a function of a column, a row constructor or an `IN (subquery)`), each `None.` when empty, each Fingerprint once per reason, both counted in the header (`Skipped queries`, `Unparsed queries`); which section a reason goes to is decided in one place in the Analyzer, never from the reason text. A skipped Fingerprint was explained and is accounted for as such. Never contains bindings or raw `attached_condition` text.
- **Redundant existing indexes (decision, user, 2026-11-03):** the Report ends with a "Redundant existing indexes" section (`None.` when empty, counted in the header) covering the tables of the connection's default database the run's explained plans read, through any access (no full-schema scan), of at least the table-rows threshold. An index is listed when it is visible, not the primary key and not FULLTEXT or SPATIAL, and another visible index on the table covers it: an exact duplicate (same columns in the same order, same type; the unique or primary one is kept, else the first by name) or, for a non-unique one, a B-tree whose declared columns it is a strict left prefix of. A unique index is listed only as an exact duplicate of the primary key or of another unique index (the primary key is kept, else the first by name; ticket 031), with a note that the index kept enforces the same constraint, and never on a table without a primary key (InnoDB then clusters the rows on its first NOT NULL unique index, which the index list does not tell apart, and dropping that one needs a full table copy). A column indexed on a prefix of its values matches only the same prefix (the Driver reads `SUB_PART`), and a functional key part matches none; the key parts compared must run in the same directions or all reversed (the Driver reads `COLLATION`), since `(a, b DESC)` serves `ORDER BY a, b DESC`, which `(a, b)` and `(a, b, c)` do not. Each entry names the redundant index and the one covering it (the one with the most columns first, so dropping every listed index keeps it), a "Primary key order" caveat on InnoDB when the covering index does not hold the order the redundant one holds with the appended primary key (`(a)` is ordered by `(a, id)`, `(a, b)` is not), and a "Foreign keys" caveat (the covering index starts with the same columns, so MySQL lets it back the foreign key, but verify the constraints before dropping). An index a Suggestion extends is not listed: that Suggestion carries a Note saying it is redundant. Sorted by table, then index name. db-hound never drops anything.
- **Dump:** JSONL; always includes decrypted Sample SQL and raw `EXPLAIN` JSON (which can contain literals); always `0600`, `-SENSITIVE` suffix, warning printed. Its `schema` holds every table the explained statement reads, at any depth, once, by its real name: row count, engine, indexes (with prefix lengths and descending key parts), column types and per-column cardinality (`{}` when MySQL has none). A table the statement names after FROM or a JOIN that is missing from it (an UPDATE's `SET` subquery reads one the explained SELECT does not) is named in `schema_error`, which is never null when a table is missing.
- **Commands:** `db-hound:flush`, `db-hound:prune`, `db-hound:analyze`, `db-hound:dump`. The package registers flush/prune on the scheduler (overridable).
- **Never runs DDL.** Migrations are written by the local agent and shipped through the team's normal process.

## Testing Decisions

- Good tests assert external behavior at the highest seam that is practical: what a command writes, what a Store holds, what Suggestions come out for given inputs. They do not assert internal method calls or intermediate data structures.
- **Seams (highest first):**
  1. **Commands end-to-end (integration):** seed a MySQL table above the row threshold with a known missing index, execute queries through `DB` with capture enabled, run `flush` → `analyze`, assert the Report suggests exactly the expected index (and nothing for already-indexed queries).
  2. **Capture → Store (integration):** execute real queries, assert Store aggregates (counts, Fingerprints, Sample encrypted, exclusions). One shared Store contract suite runs against Redis and file drivers.
  3. **Analyzer (unit):** fake Driver fed by recorded `EXPLAIN` JSON and schema fixtures captured from real MySQL; assert Suggestions (ordering, consolidation, dedupe, extend-existing, ranking, skipped, unparsed).
  4. **Fingerprinter and Report renderer (unit):** pure input → output.
- **Infrastructure:** Docker Compose with MySQL 8.0, MySQL 8.4 and Redis for local runs; same as GitHub Actions services. Integration tests live in a Pest `integration` group.
- **CI matrix:** latest dependencies only, Laravel 13, Ubuntu. Unit tests on PHP 8.4/8.5; integration tests on PHP 8.4 × MySQL 8.0/8.4 with phpredis. The package requires `ext-redis`; Predis is not supported.
- **Prior art:** only the Spatie skeleton exists (Testbench `TestCase`, Pest, arch test against debug functions). The default SQLite testing connection is insufficient for integration tests and will be replaced/augmented with a MySQL connection.

## Out of Scope

- Postgres, SQLite or other engines (Driver interface only).
- Covering-index Suggestions.
- Unused existing-index warnings (needs `performance_schema`). Redundant ones (exact duplicates and left prefixes) are reported for the tables the run's explained plans read.
- Per-table write-profile / write-heavy warnings.
- Suggestions table, dismiss/applied state, web dashboard, Pulse card, Slack notifications.
- Running DDL or generating migrations from the package itself.
- Automated transfer of the Report off the production host (engineer uses SCP).
- `EXPLAIN ANALYZE`.
- Indexing negated predicates: `!=`, `<>` and `NOT IN` match nearly every row and stay unindexable. A query whose only predicates on a table are `!=`, `<>` or `NOT IN (…)` of values is listed as skipped ("only negated predicates", ticket 031); a `NOT IN (subquery)` is a predicate db-hound does not read as an index's, so a query filtering only on it is listed as unparsed. Either way no Suggestion is made.
- Write-amplification trade-offs beyond write-hot columns (e.g. one index instead of two on an insert-heavy log table): left to the future analyze skill (the agent reading the Report), not the analyzer.

## Further Notes

- Production deployments that are containerized may need `kubectl cp` or equivalent instead of SCP; the Report path should be stable and documented.
- `phpmyadmin/sql-parser` is the only new runtime dependency besides Redis (via Laravel's Redis facade).
- With retention at 30 days, a Report reflects up to 30 days of traffic; lower `prune_after_days` for fresher Reports.
